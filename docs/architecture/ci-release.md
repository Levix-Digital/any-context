# CI and Release

GitHub Actions workflows that test the workspace and build and publish release packages.

## Responsibilities

- Run the full Rust workspace test suite on Linux and Windows for pull requests into `dev` and `main` and pushes to `dev`.
- Build, verify, package and publish the release binaries for every `v*` tag: `-rc` tags as pre-releases (release candidates), other tags as the latest release.
- Create the final tag and release when the user merges into `main`.
- Ship the official ONNX Runtime library inside the release packages.
- Keep the build fast with sccache and a dependency cache.

The release notes are generated by GitHub; architecture documentation never records release history.

## Structure

| File | Role |
|---|---|
| `.github/workflows/e2e-tests.yml` | "Rust Workspace Test Suite": `cargo test --workspace` on `ubuntu-latest` and `windows-latest`. |
| `.github/workflows/release.yml` | "Build and Release Binaries": build, verify, package and publish; also a reusable workflow. |
| `.github/workflows/tag-on-merge.yml` | "Tag on Merge": final tag from `version.txt` on pushes to `main`, then the release. |
| `.github/release.yml` | Release notes categories. |
| `scripts/fetch_onnxruntime.sh` | Downloads and verifies the official ONNX Runtime CPU build. |
| `Cargo.toml` | Workspace members and build profiles. |

## Behavior

### Build settings

The workspace (`crates/any-context-core-rs`, `actx-installer`, `actx-lm`, `actx-agent`, `actx-cli`, `actx-onnx`, resolver 2) uses `[profile.release]` with `opt-level = 3`, `codegen-units = 16`, `lto = "off"`, `strip = true` and `debug = false`; `[profile.dev]` uses `opt-level = 0` and `debug = 1`. Both workflows use `dtolnay/rust-toolchain@stable`, `arduino/setup-protoc@v3`, `mozilla-actions/sccache-action@v0.0.11` (`SCCACHE_GHA_ENABLED`, `RUSTC_WRAPPER=sccache`, statistics printed at the end) and `swatinem/rust-cache@v2` with `cache-targets: "false"` so only the crate registry is cached.

### Test workflow

Triggered by pull requests into `dev` and `main`, pushes to `dev` and manual runs; runs are grouped per pull request number (or commit) and superseded runs are cancelled. Before `cargo test --workspace --verbose`, it runs `fetch_onnxruntime.sh .ort` and sets `ORT_DYLIB_PATH` to the downloaded library and `ACTX_REQUIRE_ORT=1`, so the neural re-ranker tests are mandatory instead of being skipped.

### Release workflow

Triggered by `v*` tags, manually, and as a reusable workflow (`workflow_call` with input `tag`). The tag being released (`RELEASE_TAG`) is the input or the pushed ref, and that ref is checked out; publishing happens only for tags or calls (`PUBLISH`). Tags containing `-rc` (`IS_RC`) are release candidates. For each of `ubuntu-latest` and `windows-latest`:

1. Free disk space (Linux), then `cargo build --release -p actx-cli -p actx-installer -p any-context-core-rs` in a single invocation.
2. `fetch_onnxruntime.sh dist`: downloads ONNX Runtime 1.31.0 (`onnxruntime-win-x64-1.31.0.zip` or `onnxruntime-linux-x64-1.31.0.tgz`) from the Microsoft GitHub release, checks the pinned SHA-256 and copies `onnxruntime.dll` or `libonnxruntime.so`.
3. Verify the executable imports: on Windows, `actx.exe` and `actx-installer.exe` must not import `onnxruntime.dll`, `DirectML.dll`, `d3d12.dll`, `dxgi.dll`, `MSVCP140.dll`, `MSVCP140_1.dll` or `VCRUNTIME140_1.dll` (checked with `pefile`); on Linux, `actx` must not have ONNX Runtime as a `NEEDED` entry (`readelf`).
4. Run the live catalog test (`cargo test --release -p any-context-core-rs --lib catalog_urls -- --ignored`): every model file URL must answer HTTP 200 with the exact size.
5. Package: `actx-windows-x86_64.zip` (`actx.exe`, `actx-core.exe`, `actx-installer.exe`, `onnxruntime.dll`; `7z -mx=3` or `tar -a`) and `actx-linux-x86_64.tar.gz` (`actx`, `actx-core`, `actx-installer`, `libonnxruntime.so`). `actx-core` is a copy of `actx` kept for legacy updaters.
6. On tags and calls, publish to `Levix-Digital/any-context-releases` with `softprops/action-gh-release@v2` (token `RELEASES_PAT`, falling back to `GITHUB_TOKEN`) and `generate_release_notes: true`. Published files: the package archive, `actx-installer`, the standalone `actx` binary under its plain name, its platform name (`actx-linux-x86_64`, `actx-windows-x86_64.exe`) and the `actx-core` copy, plus the platform's install and uninstall scripts. Release candidates are published with `prerelease: true` and `make_latest: false`, so `/releases/latest` (used by the install scripts and `actx --check-update`) keeps pointing at the last final release.
7. Without a tag, upload the binary as a workflow artifact for debugging.

There is no macOS build.

### Release flow

1. Work lands in `dev` through pull requests, each tested by the test workflow.
2. The version is bumped in `dev` (`version.txt` and every crate `Cargo.toml`, the `devops.version_files` of `.dev-cycle.json`).
3. A release candidate tag `vX.Y.Z-rc.N` is pushed from `dev`; the user installs it with `actx-installer --version=<tag>` and runs `tests/MANUAL_TESTS.md`.
4. After acceptance, the user merges `dev` into `main`. `tag-on-merge.yml` reads `version.txt`, creates the annotated tag `vX.Y.Z` with `GITHUB_TOKEN` when it does not exist and calls `release.yml` with that tag (`secrets: inherit`) in the same run, because a tag pushed with `GITHUB_TOKEN` does not trigger workflows. When the tag exists already, nothing is released.

### Release notes

`.github/release.yml` groups pull requests by label into "Features & Enhancements" (`feat`, `feature`, `enhancement`), "Bug Fixes" (`fix`, `bug`, `bugfix`), "Documentation" (`docs`, `documentation`) and "Maintenance & Performance" (`chore`, `perf`, `refactor`, `test`, `ci`, `build`).

## Interfaces

- **Produces**: the release assets consumed by the [installer and updater](installer.md) and the bootstrap scripts.
- **Depends on**: the ONNX Runtime library loading rules of [ONNX Inference](onnx.md) and the catalog of [Model Catalog and Hardware Profiling](model-catalog.md).
