# Ingestion pipeline — target design (v2)

Living document of the ingestion pipeline review. Each step was filled in after being
discussed and decided. This document is the basis for rebuilding the backlog
(`docs/BACKLOG.md`).

## Principles

- **Multilingual.** AnyContext is global: no design or architecture decision is tied to one
  language or alphabet. Where choosing a language is unavoidable (e.g. text generated by
  the pipeline itself), English is chosen.
- **Explicit action.** Nothing is indexed without the user having chosen the source
  (step 1).
- **Air-gapped by default.** No ingestion step depends on a third-party service; extra
  capabilities come from local ONNX models, updated through the verified catalog.
- **Minimal configuration.** Architecture decisions (chunk size, overlap, models per role,
  thresholds, compaction…) do not become user options, not even advanced ones: they are
  decided by AnyContext and tuned by the evaluation. The user configures only what is
  theirs (sources, include filters, domain pack, privacy policies, crawl ceiling).
- **Nothing disappears silently.** What is not indexed (format without a parser, protected
  file, discarded chunk) is reported with the reason.

## Overview (happy path)

1. Source selection
2. Acquisition (download / read)

4. Content classification
5. Parsing and chunking
6. Quality gate and Document AI

## 1. Source selection

### Decisions

- **Every source comes from an explicit user action.** There is no implicit fallback: a
  workspace without sources indexes nothing (today sync indexes the current directory when
  the workspace has no folders — that goes away).
- **There is no default unit; the user chooses** between:
  - local folder, indexed recursively;
  - single local file;
  - whole website, crawled recursively;
  - single web page.
- **Connectors** follow the same rule: a target and the single or recursive mode
  (`connectors-v2.md`; web sources are themselves a connector there).
- **Per-workspace scope kept.** Each source belongs to a workspace, and no query crosses
  workspaces (see `deployment-architecture-v2.md`, workspace model). AnyContext's own
  documentation stops being the `Global` workspace and becomes the system help (below).
- **Include/exclude filters leave the code** and move to `settings.db`, with the current
  list of ignored folders and extensions as the default, configurable by the user.
- **Unused columns leave the schema:** in `workspace_web_urls`, no code reads or writes
  `title`, `last_hash`, `polling_interval_hours`, `last_scraped_at`, `page_count`,
  `root_url` and `scope`.

### Single source model

A `sources` table in `settings.db` replaces `workspace_folders`, `workspace_web_urls` and
`workspace_sources` (the unused columns disappear with them):

| column | content |
|---|---|
| `id`, `workspace` | identity and scope |
| `kind` | `local`, `web`, `builtin`, `connector:<name>` |
| `target` | path or URL |
| `recursive` | `true` for a folder or site, `false` for a file or page |
| `display_name`, `created_at` | display and audit |
| `filters` | filter adjustments for this source (optional) |
| `account_ref`, `target_id` | connectors only: credential reference and native target ID (`connectors-v2.md`, decision 12) |

### Filters

- Global defaults in a `settings.db` table, filled on creation with the current list of
  ignored folders and extensions; each source can override them.
- `.gitignore` syntax, evaluated with the `ignore` crate (ripgrep's). The `.gitignore` of
  indexed folders is honored by default, with an option to turn it off.
- Only extensions some parser supports get in; the user can turn an extension off or map
  an unknown extension to the text parser.
- A file selected on its own ignores the exclude filters: the user chose it.

### Recursive website

- Stays on the same host and inside the path prefix of the given URL (`docs.x.com/v2/`
  does not climb to `docs.x.com/`) and honors `robots.txt`.
- Generous default ceiling: **3000 pages**, configurable globally and per source.
- When the site has more pages than the ceiling, the user is told (how many were indexed,
  that there is more to index) and is given the command or setting that raises the
  ceiling of that source.
- A single page fetches only that URL, without following links.

### System help (former `Global` workspace)

AnyContext's documentation **is not a workspace** and is never mixed into the results of a
user workspace. It is an internal source (`builtin`), embedded in the binary and processed
by the same pipeline as the others (no chunker or writer of its own), in a separate, fixed
index that ships with each version and needs no sync. It is consulted only when the
question is about AnyContext itself, through the `anycontext_help` tool
(`retrieval-pipeline-v2.md`, step 1).

## 2. Acquisition (download / read)

### Decisions

- **Local files are read at the origin**, without copying, and **only once** per file: the
  same buffer feeds the hash, the parser and the enrichment (today there are up to three
  reads).
- **Documents linked from a site** (PDF, DOCX etc.), within the source scope, are
  downloaded and go through the pipeline like any file.
- **Incremental web re-sync:** ETag, `Last-Modified` and the sitemap `lastmod` avoid
  downloading what did not change (conditional requests).
- **Pages that disappear from the site leave the index.**

### Web: rendering and conversion to Markdown

AnyContext is born air-gapped: no acquisition step depends on a third-party service. **The
Jina Reader is removed entirely** (code, configuration and `JINA_API_KEY`).

1. **Rendering:** an **embedded headless Chromium** renders the pages, so that SPA sites
   (common for the target audience: home use, lawyers, accountants) arrive with content.
2. **Content selection:** a small ONNX **classification** model (not generative) marks
   each DOM block as content or noise (menu, footer, advertising). Without the model
   installed, a Readability-style heuristic plays the same role.
3. **Deterministic conversion:** the selected blocks become Markdown in Rust, preserving
   headings, tables, lists and code blocks without rewriting text.

A generative HTML → Markdown model (ReaderLM-v2) was discarded: too slow on CPU, it can
alter numbers and code, and its license needs confirmation for commercial use.

### Chromium: distribution and security

- **It ships in the installer.** Downloading it on demand (through the verified model
  catalog) is left for future reevaluation, if the installer gets too heavy.
- **It is updated with every AnyContext release**: an outdated browser opening arbitrary
  sites is attack surface.
- It runs with the sandbox on, a disposable profile per run, downloads disabled and a
  timeout per page.

### When to render

Only when needed — and the classification cannot get it wrong. That is why it **measures
instead of guessing**, and when in doubt it renders (the acceptable error is spending time,
never losing content):

1. **Per-site calibration:** on the first pages of the source (a small sample, e.g. 5), the
   pipeline does both — static fetch and rendering — and compares the extracted text. If
   the static fetch brings practically all the rendered content (e.g. ≥ 95% of the text in
   every sample), the site is **static**; otherwise, **rendered**.
2. **Per-page check:** even on a static site, a page whose static fetch comes back empty,
   very short or with signs of a JavaScript app (empty mount point, `<noscript>` asking for
   JavaScript) is rendered.
3. **Recalibration:** the classification is stored on the source and rechecked on each
   sync with a sample page; if it diverges, the site goes back to calibration.
4. **Transparency:** the mode of each site (static or rendered) appears in the source
   status, and the user can force rendering.

## 3. Incremental diff

### Decisions

- **Change is decided by the content hash.** mtime + size are only the fast filter: if
  they did not change, the file is skipped without reading; if they changed, the hash
  decides. A file touched without a content change only updates the mtime cache.
- **Rename and move are identified by the content hash** (a file that vanished and a new
  one with the same hash, in the same source) and only update the chunks' path — no
  re-embedding. Replaces the current name-and-size heuristic. Connectors use the origin's
  native ID instead (`connectors-v2.md`, decision 1).
- **Per-chunk diff.** The chunk id becomes the hash of the embedded text (plus the
  embedding target). On an edit, the file is re-chunked, chunks whose hash is already
  known reuse the vector and only the new ones are embedded; those that stopped existing
  leave.
  - It works well with chunkers that cut by structure (headers, AST), whose boundaries do
    not shift with a local edit.
  - The embedded text includes the chunk header (step 7): a context that changes for the
    whole document (e.g. a document summary) invalidates all its chunks. Step 7 has to take
    that into account.
- **An unreachable source goes offline, it is not deleted.** A disconnected external drive
  or a network folder that is down keeps its chunks in the index; the source is marked
  **offline** in the status and in citations, and returns to the normal diff when it
  reappears.
  - Today it is the opposite: the files of an unreachable folder count as deleted and **are
    removed from the index** (bug to fix).
- **Duplicates and versions (audit P17).** They respect the parent–child hierarchy of the
  chunks (step 5):
  - **Exact duplicate** (same file hash): the document's whole tree — parents and children
    — is stored and embedded **once**; each location becomes an occurrence pointing to it.
  - **Identical passage in different documents** (e.g. a standard clause): the vector is
    reused through the hash of the embedded text (per-chunk diff), but the chunk **still
    belongs to its document and its parent** — merging children of different parents would
    lose the context.
  - **Near-duplicates and versions:** a fingerprint of the text (MinHash/SimHash,
    language-independent) groups very similar documents into a **version family**, at the
    document level (root of the tree). The **current version** is the one with the most
    recent document date (step 7), with the mtime as a tiebreaker; previous ones stay
    indexed, marked "previous version".
  - Retrieval prefers the current version by default and uses the whole family for
    questions about changes between versions (`retrieval-pipeline-v2.md`, step 3).
  - The user can split documents grouped by mistake or join versions that were not
    detected.
- **No silent path "healing".** The current path healer swaps a vanished folder for a
  guessed path (`Documents/`, `OneDrive/`, a sibling folder) and indexes that path without
  asking. That violates the explicit action rule (step 1): at most, AnyContext suggests
  the likely path and the user confirms.

## 4. Content classification

### Decisions

- **Classification by content, extension as a hint.** The binary signature (magic bytes)
  decides; the extension only breaks ties. A renamed file, one without an extension or
  with the wrong extension goes to the right parser.
  - ZIP containers are inspected inside: `[Content_Types].xml` separates DOCX, XLSX and
    PPTX; the `mimetype` file separates ODT, ODS, ODP and EPUB.
  - OLE/CFB containers (old Office and Outlook) are separated by their internal streams:
    `WordDocument` (.doc), `Workbook` (.xls), `PowerPoint Document` (.ppt),
    `__substg1.0_*` (.msg).
  - Text has its **encoding detected** (UTF-8, UTF-16 with BOM and the legacy encodings of
    any language, such as Windows-125x, Shift_JIS, GB18030) before moving on; a text that
    is CSV, JSON or Markdown is recognized by its content.
- **Categories:**

  | category | formats |
  |---|---|
  | web | pages rendered/converted in step 2 (arrive as Markdown) |
  | local HTML | `.html`, `.htm` — same converter as the web |
  | text and Markdown | `.txt`, `.md`, `.rst`, logs, scripts |
  | code | languages with a tree-sitter grammar |
  | structured | JSON, JSONL, YAML, TOML, XML |
  | tabular | CSV, TSV, XLSX, XLS, ODS, OFX |
  | PDF | digital or scanned, **per page** |
  | Office | DOCX, PPTX, DOC, PPT, ODT, ODP, RTF |
  | e-mail | `.eml`, `.msg` (body and attachments, which go back into the pipeline as files) |
  | e-book | `.epub` |
  | image | PNG, JPEG, WebP, TIFF, HEIC |

- **Old Office and ODF get real parsers** (`.doc`, `.ppt`, `.xls`, `.odt`, `.odp`, `.ods`,
  `.rtf`). Today `.doc`/`.ppt` are opened as ZIP and fail, and `.odt`, `.epub`, `.rtf`,
  `.eml`, `.msg` and `.html` are indexed as raw text or fail.
- **Each PDF page is classified into three states:** **digital**, **scanned** or **digital
  with broken text** (the text layer exists but is garbage — fonts without a Unicode
  mapping, CID —, common in old systems of courts, municipalities and hospitals). The third
  state is treated as scanned. Detection is language-independent: proportion of
  replacement, private-use and control characters, and improbable sequences; when in doubt,
  the page text is compared with a quick OCR of the same page and the better one stays
  (measure instead of guessing). Mixed PDFs — digital with scanned attachments, common in
  legal cases and accounting — send each page down the right path (text or OCR), instead
  of finding out at the quality gate.
- **A password-protected, corrupted or unsupported-format file** is not indexed and is
  reported to the user with the reason — never indexed as garbage nor dropped silently. A
  protected file can be unlocked with a password from the vault (below).

### Containers and archives (audit P1)

- **Opened recursively.** Each inner item becomes a **child document**, with chained
  provenance (`case.zip > records/attachment 3.pdf`,
  `office.pst > Inbox > Re: contract > draft.docx`), and goes through the normal pipeline
  (content classification, parser…).
- **Formats:** ZIP, 7z, TAR, GZ, BZ2, XZ, MBOX and **PST/OST** (Outlook). **RAR** read-only,
  if the decompressor's license allows it (to be confirmed legally; buying a license is
  left for future evaluation); otherwise it is refused with a clear message.
- **Protection:** depth limit (e.g. 5 levels), uncompressed size and compression ratio
  limits (zip bombs), rejection of internal paths with `../`. Whatever is blocked appears in
  the report.
- **Diff:** the container has its own hash and so does each child; when the container
  changes, only the changed children are reprocessed.
- **Citation:** shows the full path inside the container; "open the original" extracts the
  item to a temporary folder.
- The source **filters** (step 1) also apply inside the container.

### Vault of file passwords

Protected files and containers can be unlocked with passwords the user provides per source
(or per file). AnyContext **uses the password without knowing it** outside the exact moment
of opening the file:

- **Stored in the user's personal vault** (`identity-and-governance-v2.md`, topic 2).
  `settings.db` keeps only a reference (`secret_id`) on the source, never the password.
- **Only the ingestion worker reads it**, at the moment of opening the file; it stays only
  in memory, is wiped (zeroize) right after, and never goes to logs, reports, indexes or
  prompts.
- **The agent and the LLM never have access to the vault**: there is no tool that reads
  passwords, and no password enters the context of a conversation.
- **"Always ask" option**: the password is not stored and is asked for on every sync that
  needs it.
- **No trial and error:** a wrong password fails the file and is reported; AnyContext never
  tries to guess passwords.
- The vault is unlocked with the user's session (`identity-and-governance-v2.md`, topic 1).

## 5. Parsing and chunking

### Decisions

- **Size measured in tokens**, with a single target for every parser (around 512 tokens)
  and a hard ceiling at the embedding model's input limit. Today the size is in characters
  (1800) and PDF is an exception (up to 8000).
- **Overlap only in running text** (prose, PDF, Office, e-mail, web), around 10–15%. Code,
  tables and structured data are cut by structure, without overlap.
- **Hierarchical chunks (small-to-big).** The small chunk is what is embedded and searched;
  each one keeps the link to its **parent**, which is stored but not embedded and can be
  handed to the LLM instead of the chunk:

  | content | parent |
  |---|---|
  | Markdown, Office, web, e-book | section (heading) |
  | PDF | page |
  | code | function, class or module |
  | tabular | sheet + row range |
  | e-mail | message |

- **OCR through an ONNX model**, instead of the external Tesseract (today looked up on the
  PATH and often missing). Multilingual: the OCR detects the page's writing system and uses
  the corresponding recognition model. Candidate: PaddleOCR exported to ONNX (Apache-2.0,
  recognition models for dozens of languages and alphabets); alternative: docTR.
  Distributed and updated like the other ONNX models.
- **Tables repeat the header in each row chunk**, with:
  - the location in the chunk (sheet and row range) for citation;
  - wide tables (e.g. more than 15 columns) in a `column: value` record format per row,
    instead of a Markdown table row.

### Full Office and PDF (audit P6 and P7)

The parser extracts the whole document, not only the body text. Today DOCX cuts sections by
size ("Section 1, 2, 3") and ignores headings, comments, notes and tracked changes; PPTX
ignores notes; XLSX ignores formulas and merges; PDF ignores the outline, annotations,
forms, attachments and signatures.

- **Real structure:** DOCX heading styles, PPTX slide titles and the PDF outline
  (bookmarks) become the section path (step 7). Tables become Markdown tables; lists are
  preserved.
- **Tracked changes:** the main text is the **current version** (with insertions, without
  deletions); each change is indexed as **its own item** with author, date and the inserted
  or deleted passage ("who changed clause 5 and when?").
- **Comments and annotations** (DOCX, XLSX, PPTX, PDF): their own items linked to the
  commented passage, with author and date.
- **Headers and footers:** indexed **once per document**, not repeated per page. Footnotes
  and endnotes stay linked to the section where they appear.
- **PPTX:** speaker notes together with the slide.
- **XLSX:** the indexed text is the computed value; the formula stays as metadata. Merged
  cells expanded, named ranges as labels, hidden sheets indexed and marked as hidden.
- **PDF:**
  - form fields (AcroForm) as key–value pairs;
  - files attached to the PDF go through the containers (step 4);
  - **digital signatures:** signer, date and whether the document was changed after
    signing. The chain of trust is validated with the operating system's root
    certificates, with no rule tied to one country; when it cannot be validated offline,
    the status is "not verified".
- **Other formats:** calendar (`.ics`), contacts (`.vcf`) and MHTML at level 1 (simple and
  frequent); Visio (`.vsdx`), XPS and Apple iWork (Pages, Numbers, Keynote — a proprietary
  and harder format) at level 2.

### Academic, engineering, GIS and health formats (audit P3, P4 and P5)

Always available, with or without a domain pack.

- **Academic:** LaTeX by section, equations preserved in LaTeX and `\cite` linked to the
  reference; BibTeX, RIS and CSL-JSON as records (authors, title, year, DOI); Jupyter, R
  Markdown and Quarto with text cells as prose, code through the code parser, text outputs
  indexed and output images through the vision model; PDF formulas in LaTeX (page parsing
  model, step 6); Parquet and Arrow as queryable tables. SPSS and Stata come later.
- **Engineering and real estate:** DXF (texts, layers, block attributes; title block as
  fields); **DWG refused** with a message suggesting export to DXF or PDF (proprietary
  format; a commercial library license to evaluate in the future); IFC with the hierarchy
  site > building > storey > space as the section path and each element with its
  properties; STEP and IGES by the header only; title blocks of drawing sheets in PDF
  through LSIE and layout maps (step 6).
- **GIS:** GeoJSON, KML/KMZ, Shapefile and GeoPackage — each feature as a record with its
  attributes; coordinate system and covered area as metadata (spatial filters in the
  future).
- **Health:** DICOM with tags (patient, study, modality, date, description), structured
  reports and embedded PDFs — **the medical image is off by default** (only if the user or
  the pack turns it on); HL7 v2 with each segment as a record; FHIR with each resource as
  an item and references preserved; CDA by its clinical sections. Pseudonymization for a
  cloud LLM (step 7) applies at full strength.

### Audio and video (audit P2)

- **Formats:** audio MP3, WAV, M4A, OGG, FLAC, Opus; video MP4, MKV, MOV, WebM. Audio read
  in pure Rust (Symphonia), including the audio track of videos.
- **Local, multilingual transcription via ONNX** (Whisper family, MIT), with automatic
  language detection and model size per profile; a voice activity detector (VAD) skips
  silences.
- **Existing captions take priority:** an embedded caption, or an `.srt` or `.vtt` next to
  the file, is used directly, without transcribing.
- **Chunks and locators:** chunks follow sentences and speaker turns; the locator is start
  and end in seconds (step 7); the parent is a block of a few minutes or a chapter.
- **Speaker identification:** optional per profile, **on by default in the legal pack**
  (hearings). Speakers come out as "Speaker 1, 2…" and the user can name them for the whole
  file.
- **Video frames:** key frames at scene changes described by the vision model; lecture and
  meeting slides by OCR. The decoder is **FFmpeg, in the installer** (like Chromium),
  distributed as a separate library to comply with the LGPL.
- **Long job:** estimate, confirmation and progressive processing (below); the transcript
  becomes searchable as it advances.
- **Privacy:** transcription is always local; names mentioned go through pseudonymization
  when the context goes to a cloud LLM (step 7).
- Transcription of local audio and video is a capability connector
  (`connectors-v2.md`, decision 22).

### Long jobs (large spreadsheets, huge sites and folders)

There is no size limit; whether to wait is the user's call.

- **Estimate before starting:** expected chunks and estimated time **on this machine**,
  from the speed measured in previous syncs with the same `embedding_target` (the first
  time, through a quick measurement).
- **Confirmation above a threshold** (e.g. 10 minutes, configurable): index everything,
  index only part (e.g. some sheets) or skip.
- **Background and progressive:** what is already indexed is searchable right away; an
  interruption loses no work — the per-chunk diff (step 3) resumes where it stopped.
- AnyContext **does not split or alter user files**, nor suggests splitting them: the
  pipeline already slices by rows, so splitting does not reduce the work.
- Aggregate questions over large tables ("sum of March sales") are not well served by
  semantic search: storing the table in a queryable format and answering by query is
  covered by the retrieval pipeline (`retrieval-pipeline-v2.md`, step 4).

## 6. Quality gate and Document AI

### Decisions

- **The quality gate only applies safe, language-independent filters:** empty or too
  short, loose syntax (`}`, `)];`), minified line and binary (control characters). The byte
  entropy and lexical density filters go away: they discard text in non-Latin alphabets as
  "binary garbage" and tables or logs with repeated values.
- **Every discarded chunk is logged with the reason** and is visible in the sync report
  (and in an inspection command), instead of only a count.
- **Page extraction (audit P8).**
  - **Digital page:** the text layer is always the truth (it is exact). No model rewrites
    that text; a model can, at most, help discover the structure (reading order, tables)
    from the coordinates of the original text.
  - **Scanned page, broken text, photo or handwriting:** a **page parsing model** (small
    VLM via ONNX) reads the image and returns Markdown with reading order, tables, formulas
    and handwriting, on the profiles that can afford it; light profiles keep the cascade
    OCR → layout → 2D heuristic:

    | profile | scanned page |
    |---|---|
    | Lite | OCR + 2D heuristic |
    | Smart Balanced | OCR + layout model |
    | Air-Gapped Power and above | page parsing model (candidate: Granite-Docling-258M, Apache-2.0) |
    | Workstation Pro, Sovereign Ultra | a larger model if it wins the benchmark (candidate: PaddleOCR-VL, license to be confirmed) |

  - **Benchmark before fixing the models:** Granite-Docling, PaddleOCR-VL and the
    OCR + layout cascade measured on a real set of scanned pages, tables, forms and
    handwriting (quality and time per page on CPU, per profile).
  - Long scanned documents use the estimate, confirmation and progressive processing of
    long jobs (step 5).
- **Forms as data (LSIE).** Forms (CMR, invoice, payslip, timesheet, bank statement,
  medical report, court form…) must not have values bound to the wrong label. Test with a
  real CMR: the current extractor produced a single chunk of broken tables and assigned the
  actual departure time to the actual arrival.
  1. **Known layout:** the layout is recognized by geometry (lines and boxes) and fixed
     labels; with the stored map, **LSIE** (Levi's Scale-Invariant Extraction, from
     DocMapper) extracts deterministically — milliseconds, invariant to scale and margins,
     it corrects fields that grow and push the others, with no leakage between fields.
  2. **New layout — automatic phase 0 per profile**, which generates the map (field, box,
     anchor label):
     - light profiles: box (vector lines) and typography heuristics (small label, larger or
       bold value), language-independent;
     - medium profiles: a small model that identifies labels and values and hands the map
       to LSIE;
     - high profiles: the page parsing model (P8) extracts the pairs directly and also
       generates the map.
     The field model license enters the benchmark (e.g. LayoutLMv3 is non-commercial;
     Ultralytics YOLO models are AGPL).
  3. **The map becomes the layout model**, reviewable and correctable by the user (a screen
     in the style of DocMapper's Mapping Studio); the next documents of the layout use LSIE.
  4. **Anomaly gate with a local model** (in DocMapper it is Gemini): cloud only by explicit
     configuration.
  5. **Anchored values:** on a digital page, every value must exist in the text layer; no
     model invents a number.
  6. **Output:** each field becomes a pair of field number + label as in the document +
     value; the form is stored as a record, and **forms of the same model become a
     queryable table** (one row per document, one column per field).
  7. **Test corpus per sector** with the expected pairs, running on every change; it starts
     with the fictitious CMR in `crates/any-context-core-rs/tests/fixtures/forms/`.
     Self-evaluation (H1) warns in production about empty or low-confidence fields.
  - **Single implementation:** LSIE is ported to a shared Rust crate, also compiled to WASM
    and used by DocMapper — one engine for both products (`levix-platform`).
  - **DocMapper integration:** the layout map format is common to both products (a layout
    mapped in one serves the other), and AnyContext can hand over to DocMapper what belongs
    to it (advanced visual mapping, PDF stamping, field export). AnyContext works without
    DocMapper installed, and the integration is local, with no cloud.
- **Local Document AI via ONNX.** On profiles with the cascade, after OCR (step 5), a
  **layout** model rebuilds scanned tables and forms; the current 2D spatial heuristic
  stays as a fallback.
  - A vision LLM (local or in the VPC) only if the user configures it explicitly; off by
    default. Never an implicit external service.
  - Today no Document AI component is wired in production (layout extractor, scan detector
    and vision mode are never connected): every candidate falls to the 2D heuristic.
- **Images that are not text** (photos, diagrams, charts) receive a **description generated
  by a local vision model** (ONNX), indexed together with the OCR text and the metadata. The
  description is generated in English (multilingual embedding brings it close to questions
  in any language).

### Vision model per profile

The vision model is part of the model kit. Starting point, **to be validated by a
benchmark** (a set of real photos, diagrams, charts and documents; description quality and
time per image on CPU on each profile) before being fixed:

| profile | vision model |
|---|---|
| Lite (<8GB) | Florence-2-base (0.23B, MIT) |
| Smart Balanced (8GB) | SmolVLM-500M (Apache-2.0) |
| Air-Gapped Power (16GB) | SmolVLM-2.2B (Apache-2.0) |
| Workstation Pro (32GB), Sovereign Ultra (64GB+) | the profile's local Gemma (FEAT-002, multimodal), with no extra model; SmolVLM-2.2B if there is no ONNX export |

Progressive processing: the image becomes searchable first through OCR and gets the
description in the background.

## 7. Chunk headers and metadata

### Decisions

- **Metadata and embedded text are separate things.**
  - **Metadata** (columns, never embedded): `source_id`, `workspace`, path or URL, content
    type, location (page, section, lines, spreadsheet range), `parent_id` (step 5), hashes
    and dates. Connector live metadata also lives here only (`connectors-v2.md`,
    decision 14).
  - **Contextual header** (embedded): only **document title + section path** (e.g.
    `Lease Agreement > Clause 5 > Penalty`). Short, stable under body edits — it does not
    break the per-chunk diff (step 3) — and language-independent. In the lexical index the
    header is weighted lower than the body (or has its own field).
- **`embedding_target` on each chunk** (provider, model, dimension), instead of a single
  record per workspace: it allows migrating models gradually and knowing exactly what needs
  reindexing.
- **The current envelope goes away** (summary of the first sentences + 7 keywords by
  frequency, prefixed to every chunk): all chunks of a file hit the same words in BM25, an
  edit at the start of the document invalidated all chunks, and the stop-word list was
  English and Portuguese only. The `// Context: …` breadcrumb inside the text also goes —
  the contextual header replaces it.

### Precise locators (audit P22)

Each chunk stores a locator specific to its content type, to open the original at the exact
point and highlight the passage (FEAT-016):

| content | locator |
|---|---|
| PDF and image | page + region on the page (rectangle) |
| spreadsheet | sheet + cell range (`Sales!B300:F340`) |
| audio and video | start and end in seconds |
| text, code, Markdown | lines |
| Office | section + paragraph |
| web | URL + section anchor |
| container | internal path (step 4) + the item's locator |
| form | field + region |

In the parent–child hierarchy (step 5), the **child** has the precise locator and the
**parent** has the extent covering all its children (e.g. page range of the section, row
range of the spreadsheet), so that both the passage and the larger context handed to the
LLM are citable.

### Visual page retrieval (audit P10)

- **Only visually rich pages** (charts, diagrams, drawing sheets, slides with diagrams,
  handwritten forms — identified by the layout and page parsing, step 6) receive embeddings
  of the **page image** (ColPali family: one vector per image region).
- In retrieval they enter as **one more list** (`retrieval-pipeline-v2.md`, step 4); the
  result is the **page** (the parent of its chunks); the reranker judges the page by the
  text ingestion produced from it (parsing and description).
- With a **multimodal** chat model, the page image goes as evidence, respecting the trust
  level and the confidential ceiling; **workspaces with pseudonymization active do not send
  images to an external endpoint** (pseudonymization does not reach the image content).
- **Per profile, via ONNX:** off on light profiles; a small model (ColSmol family) on medium
  ones; a larger one (ColQwen family) on strong ones and on the Model Server — chosen by
  benchmark (ViDoRe) and permissive license.
- **Vectors stored in full** (they are few pages); compaction only without measurable loss
  (P18 rule).

### Entity and relation graph (audit P16)

1. **Base graph, without an LLM:** nodes = documents, entities (P12) and sources; edges =
   "entity appears in the document" and structural relations known for certain —
   attachment of (containers), version of (P17), replies to (e-mail), cites or references
   (links and citations between documents, Obsidian wikilinks). **Entity resolution** by
   spelling and embedding similarity ("Supplier X Ltd." = "SUPPLIER X LTD"), correctable by
   the user (merge, split). It already answers "documents that mention X and Y" and allows
   browsing by entity.
2. **Typed relations by an LLM** (e.g. "X is a party in case Y", "drug M prescribed to
   patient P"): only on profiles with a local LLM, in the background; **types coming from
   the domain pack**; **every relation keeps the passage it came from** (citable) and a
   confidence — a relation without evidence does not get in.
3. **Use in retrieval:** an extra list in search (entities in the question pull the linked
   documents), an LLM tool ("query relations", useful in Deep) and a structured source for
   enumerative questions.
4. **One graph per workspace**, never crossing workspaces, encrypted with the workspace
   key; on by default only with a gain measured by the evaluation set. An entity view in
   the inspector as a Tauri UI item.

### Hierarchical summaries (audit P14)

- The tree gains levels above: **folder > document > section (parent) > chunk**. Document
  and folder receive a **summary generated by the profile's local LLM**.
- Summaries are **their own nodes**, embedded and searchable — never prefixed to chunks.
  They answer overview questions and help choose which documents to search before going
  down to the passages (`retrieval-pipeline-v2.md`, steps 3 and 4).
- Regenerated only when the content changes (by hash), in the background.
- Language: a document summary in the document's language; a folder summary with documents
  in several languages in English.
- Profiles without a local LLM have no summaries, unless a cloud LLM is explicitly
  authorized.

### Late chunking (audit P15)

- The embedding model reads the whole **parent** (the section) and each chunk receives a
  vector with the surrounding context, at no LLM cost. An edit re-embeds only the children
  of that parent, preserving the per-chunk diff.
- Only with a **local long-context** embedding model (e.g. BGE-M3, 8192 tokens); cloud APIs
  do not expose what is needed and 512-token models do not work.
- Per profile: with a local LLM, contextual retrieval (below); light profiles with
  long-context embedding, late chunking; the others, only the title + section header.
- Published gain is modest (≈ 3%): **on by default only if the self-evaluation set shows a
  gain** in the workspace.

### Document metadata and entities (audit P12)

- **Document metadata:** language, **document date extracted from the content** (not the
  file mtime), type, title and authors.
- **Entities with types configurable per workspace** (e.g. "case number", "patient",
  "sheet number", "tax identifier"), extracted by a zero-shot multilingual model via ONNX
  (candidate: GLiNER, Apache-2.0; license of each checkpoint to be confirmed). They become
  filters and facets in retrieval ("contracts with party X signed in 2025").

### Personal data, sensitive data and secrets (audit P13)

- **Personal and sensitive data:** the same model tags generic categories (name, identity
  document, health, financial data, contact) — with no rule tied to one country; it serves
  LGPD, GDPR, HIPAA. Protection can never make the source unsearchable: a case number, a
  medical record number or a license plate are precisely the most common way to search.
  1. **Search: nothing is masked.** The index stores the identifiers (encrypted on disk)
     and searching for them always works, by exact match and by filter.
  2. **The user always sees the real values.**
  3. **External endpoint: reversible pseudonymization.** Before sending the context, each
     personal identifier becomes a consistent marker (`[PERSON_1]`, `[RECORD_1]`); the LLM
     answers with the markers and AnyContext restores the real values locally before
     showing the answer. The content (diagnosis, clause, cargo) still goes — what is
     protected is **who it refers to**. The domain pack defines which entity types are
     pseudonymized (e.g. health — patient and medical record yes, diagnosis code no). With a
     local or corporate endpoint (see trust levels in `deployment-architecture-v2.md`),
     nothing is pseudonymized by default.
  4. **"Do not index"** only for secrets and by explicit user choice — never as a default
     pack policy.
- **Secrets** (API keys, tokens, passwords, private keys) are detected by known patterns
  and entropy, as in the market's secret scanners, and **the value is never indexed, with
  no configurable exception**: it becomes `[SECRET REDACTED]` and the rest of the file
  stays useful. Today the scanner indexes `.env`, `.tfvars` and configuration files in
  clear, and those secrets can reach a cloud LLM.

### Contextual retrieval (local LLM)

An LLM generates one context sentence per chunk, which goes into the embedded header. It is
a **capability of the model kits (hardware profiles)**:

- On by default on profiles with room for a local LLM (e.g. Workstation Pro and Sovereign
  Ultra), off on the others; the user can change the setting.
- It uses the profile's own local LLM (no extra model) and never an implicit external
  service; an LLM in the VPC only by explicit configuration.
- **Progressive enrichment:** the chunk is first indexed with only title + section
  (already searchable) and is re-embedded with the context in the background, without
  blocking the sync.
- **The identity of the context model enters the chunk key**, together with the
  `embedding_target`: turning it on, off or switching the model changes the embedded text,
  and AnyContext warns and reindexes the affected chunks (the same rule as an embedding
  model switch).

## 8. Embedding

### Decisions

- **The embedding model is independent of the chat model** (FEAT-005). It is defined by
  the model kit (hardware profile) and the user can change it. Today it is derived from the
  chat model, and switching chat reindexes the whole workspace.
- **Local, multilingual default, via ONNX** — AnyContext is born air-gapped. The model
  varies by profile; candidates with a permissive license: `multilingual-e5-small`/`-base`
  (MIT), `BGE-M3` (MIT; 100+ languages, 8192 tokens, also sparse vectors) and
  `Qwen3-Embedding-0.6B` (Apache-2.0). Cloud providers (OpenAI, Gemini…) only by explicit
  choice.
- **Never switches model silently.** The fallback to OpenAI and to the mock provider (fake
  vectors) ends. If the chosen model fails, the files fail, the user is told and the next
  sync tries again.
- **Prefixes per model:** the catalog declares each model's query and document prefixes
  (e.g. `query:` / `passage:`) and the pipeline applies them at ingestion and at query
  time (IMP-014).
- **Batches limited by tokens and by the API maximum**, with controlled parallelism for
  remote providers and use of the available CPU/GPU in the local case. Today it is one call
  per file, without a limit, one at a time.

## 9. Lexical indexing (BM25)

### Decisions

- **Tantivy (MIT) replaces the in-house implementation.** On-disk, incremental,
  segment-based index (without loading everything into memory or rewriting the whole file
  on each sync), fields with different weights (header weighted lower than the body,
  step 7), pluggable tokenizers and native BM25.
- **The index does not store the chunk text**, only the terms and the id; the text comes
  from LanceDB. Today `bm25_index.bin` stores the full text in clear and defeats LanceDB's
  encryption (IMP-012).
- **The index files are encrypted on disk**, through Tantivy's own storage layer
  (`Directory`) — a lexical index always contains the terms in clear, so protection happens
  in storage.
- **One index per workspace.** The statistics (IDF, average length) of one workspace do not
  affect the ranking of another; deleting a workspace deletes its directory. No query
  crosses workspaces.
- **Multilingual tokenization without per-language tables:**
  - word segmentation by the Unicode standard (UAX #29), with a dictionary for languages
    without spaces between words (Chinese, Japanese, Thai, Khmer…) — ICU4X, in Rust;
  - generic accent removal, by Unicode normalization (NFKD without combining marks), for
    any alphabet, instead of the manual Latin-only table;
  - code identifier splitting (`camelCase`, `snake_case`) kept, together with the whole
    identifier.
- **No stemming:** it depends on the language; semantic search covers word variations.
- **Learned sparse vectors (audit P19):** only when the profile's embedding model already
  produces them in the same pass (e.g. BGE-M3) — no extra model. Stored in the lexical index
  as a field with each term's weight (per workspace, encrypted); they enter as an extra list
  in RRF; on by default only with a gain measured by the evaluation set. With cloud
  embedding or without sparse output, they are left out at no loss.

## 10. Persistence in the vector store

### Decisions

- **Physical isolation per workspace.** Each workspace has its own LanceDB tables (like its
  lexical index, step 9), instead of the single `workspace_chunks` table filtered by the
  `workspace` column — where a forgotten filter leaks data between workspaces (BUG-023).
  Deleting a workspace is deleting its directory.
- **One table per workspace and per `embedding_target`**, with the model's real dimension:
  zero-padding up to 1536 ends (IMP-004). On a model switch, the new table is filled while
  the old one keeps answering, and the old one is dropped at the end.
- **Automatic maintenance:** compaction after syncs with many deletes or reindexes
  (IMP-013). Migrations leave the sync path: the schema is versioned and migrated once, when
  the store is opened.
- **Encryption key:** replaced by the key hierarchy of `identity-and-governance-v2.md` — a
  data key per workspace, wrapped by the user's master key (released by the password,
  recovery key or biometrics). The current key, derived from the machine id with a salt
  fixed in the code, goes away.
- **Approximate vector index (ANN) from 100 thousand chunks** per workspace and
  `embedding_target`, configurable. Below that, search is exhaustive (exact and fast —
  thousands of files stay in the tens of thousands of chunks). Above it, the index is
  created automatically in the background and rebuilt after many changes; newly inserted
  chunks not yet in the index are still found (exhaustive search over the new ones, fused
  with the ANN). The small recall loss of ANN is compensated by the parallel lexical search
  and the reranker.
- **Compact vectors (audit P18) — quality first.** What was indexed (text, chunks, metadata
  and full vectors) never changes; compaction only creates a shortcut to find candidates,
  and the final order is always computed with the full vectors.
  1. **No compaction by default.** It is only turned on by real need: the index does not
     fit comfortably in memory or search gets slow (typical of light profiles with large
     workspaces). int8 or binary quantization, reversible without reindexing.
  2. **Practically zero tolerance:** with compaction, the sieve fetches more candidates
     (e.g. 4×) and it only stays active if the evaluation set shows no measurable loss (up
     to 0.5 percentage points in hit rate).
  3. **Internal mechanism:** the evaluation runs again after relevant syncs and, if a loss
     appears, compaction is turned off automatically. The user is neither told nor asked —
     no content is lost, it is only a search mode; the record stays in the diagnostics.
  4. **Matryoshka truncation is never used:** it discards information in storage, which is
     not acceptable. Vectors are always stored at the model's full dimension.
- **Vectors protected in the storage layer.** Per-field encryption does not work for them
  (search computes distances over the vectors), so the LanceDB files are encrypted on disk,
  through a storage layer of its own, with the workspace data key. Since LanceDB does not
  offer this out of the box, AnyContext builds that layer (like Tantivy's encrypted
  `Directory`, step 9).

## Cross-cutting: ingestion self-evaluation (audit H1 and H2)

Inspired by Harness²'s propose–probe–compose: ingestion measures its own quality, without
ground truth, and fixes what came out poorly.

1. **Deterministic signals (every profile, no LLM):** extraction quality score per file,
   from text extracted per page and empty pages, proportion of broken text (step 4), OCR
   confidence, filled form fields relative to those expected from the layout map, chunks
   discarded by the quality gate and parser errors.
2. **Probing with synthetic questions (profiles with a local LLM):** per source, a sample of
   chunks; for each, the local LLM generates, in the document's language, a question whose
   answer is in it; retrieval is executed and it counts as a hit if the chunk or its parent
   appears among the first results. The hit rate is the source's **findability score**.
3. **Automatic reprocessing (compose):** a file with a low score is reprocessed with an
   alternative strategy (OCR instead of the text layer, web rendering, another form
   mapping, another chunk size) and **the best-scoring strategy stays**.
4. **Strategy memory (H2):** the winning strategy is remembered per source and file type
   and applied to the next files — it generalizes the web rendering calibration (step 2).
5. **Source report:** what is still poor appears with the reason, and the user can ask for
   reprocessing.
6. **Cost and privacy:** background, low priority, sampling; only the profile's local LLM
   (cloud only by explicit configuration); generated questions stored locally and
   encrypted.
7. **Retrieval evaluation set:** the synthetic questions form an evaluation set per
   workspace, used to measure retrieval after each model or configuration change (solves
   IMP-008).

## Cross-cutting: domain packs (audit H3)

A domain pack is a **declarative** set (data only, no code) that tunes AnyContext to an
area. It is orthogonal to the hardware profiles: the profile decides what the machine can
handle; the pack decides what matters for the area.

**Launch packs (11):** **Personal** (default when none is chosen — home use: people,
places, dates, amounts, accounts, receipts, family and school documents), legal, health,
engineering, accounting, logistics, HR, academic, IT, public sector and real estate.

**Content of a pack:**

1. **Entity types** for the entity model (step 7) — e.g. legal: case number, parties,
   court, judge, deadline; health: patient, exam, drug, diagnosis code, physician;
   logistics: shipment, seal, plate, carrier.
2. **Metadata and filters** that make sense in the area.
3. **Pseudonymization for a cloud LLM:** which entity types become markers (step 7).
4. **Optional heavy processors on by default** (e.g. transcription in legal, image
   description in engineering).
5. **Question templates for self-evaluation** typical of the area.
6. **Answer guidelines** (e.g. "always cite page and field") —
   `retrieval-pipeline-v2.md`, step 8.
7. **Layout maps** only as an accelerator, for truly official and unique forms. The value
   is in **learning**: maps come, in order of importance, from the automatic phase 0 on the
   user's own machine (step 6), from DocMapper import (common format) and, optionally, from
   voluntary sharing between customers — only geometry and fixed labels, never values, and
   only with explicit authorization (a map can identify a company's form).

**Rules:**

- **Parsers always work**, with or without a pack; the pack only tunes and enriches, it is
  never a condition for a file to be understood.
- **Several packs per workspace** (e.g. legal + HR) and **custom packs** created by the
  user.
- **Multilingual:** internal field names in English; displayed labels in the UI language;
  entities detected in any language of the document.
- **Distribution** through the verified model catalog (version and hash), updatable without
  a new AnyContext version.

## Cross-cutting: automatic sync of sources (audit P20)

1. **Local sources:** watching file system changes **only on the sources the user chose**,
   with batching (a few seconds of quiet before processing as a batch).
2. **Network folder and removable drive:** periodic fallback scan, because OS notifications
   are not reliable in those cases.
3. **When AnyContext opens:** a recovery diff of what changed while it was closed.
4. **Web sources:** scheduled recrawl, daily by default and configurable per source, with
   conditional requests (step 2).
5. **Low priority**, so as not to disturb the use of the machine.
6. **Manual sync still exists**; automatic sync can be turned off per source.
7. **With AnyContext closed:** by default nothing runs (the recovery diff covers the gap);
   an **optional background service** keeps everything up to date all the time for whoever
   chooses it.

## Cross-cutting: machine resource governance (audit P21)

A **single governor** coordinates all heavy work (OCR, parsing, transcription, vision,
embedding, reranker, local LLM, self-evaluation, graph) in ingestion and search.

1. **Global priority:** user question (interactive) > base indexing > enrichments >
   self-evaluation and maintenance. When the user asks, background work yields at once
   (pauses, frees CPU, GPU and memory) and resumes afterwards.
2. **Automatic adaptation to the machine state:** on battery, only base indexing (heavy
   enrichments wait for power); low battery pauses everything; another heavy program in use
   or overheating slow the pace; a limited network (mobile data, metered connection)
   prevents web crawling and large model downloads, unless the user releases it
   (`connectors-v2.md`, decision 6).
3. **Memory:** budget per profile; models loaded on demand and unloaded when idle (least
   used first); one heavy model at a time on the GPU.
4. **Disk:** free space checked before large jobs, with a reserve — it never fills the
   disk; when space runs short, it warns and waits instead of failing midway.
5. **User:** only the "pause indexing" button and an indicator of what is happening (e.g.
   "indexing paused: on battery") — minimal configuration principle. In enterprise mode, the
   policy can define windows for heavy work (e.g. outside business hours) and a CPU usage
   ceiling.
6. **The same governor** decides the parallelism of the stratified search (retrieval,
   step 4) and the capacity of the ingestion worker.

## Cross-cutting: per-source access control (audit P23)

Rule (identity, topic 3, item 6): in a shared index, **a reader never receives chunks of
documents they cannot open at the origin**.

**Where it applies:**

- **Desktop without a server, with the workspace definition shared:** it does not apply —
  each member indexes with their own access.
- **AnyContext Server and corporate connectors** (SharePoint, OneDrive, Google Drive, file
  server): ingestion runs with a service account that sees everything, and the per-reader
  filter is mandatory.
- **Workspace shared between accounts on the same machine:** whoever shares hands over the
  indexed content — an explicit decision of the owner, with a warning in the UI ("by
  sharing, members see the indexed content of this workspace").

**Design:**

1. **Permission scope ID in the chunk.** At the origin, almost everything inherits
   permission from a point above (the `/Finance` folder, the SharePoint site, the shared
   Drive folder). Each chunk stores only the **ID of the scope** its document's permission
   comes from — never the list of who can read.
2. **Details in separate SQLite databases:**
   - **workspace scopes** (who can read each scope, captured from the origin: Windows and
     Linux ACLs, SharePoint/OneDrive, Google Drive), encrypted with the workspace key;
   - **directory users and groups** (SSO and SCIM), on the server, valid for every
     workspace.
3. **Identity linking:** users and groups of the origin are linked to corporate identities
   through the same provider (SSO and SCIM); **what does not link gets no access**.
4. **Cost of each change at the origin:**

   | Change | What is updated |
   |---|---|
   | someone joins or leaves a group | only the users and groups database |
   | the permission of a folder or site changes | only the scope row in SQLite — nothing in the index, even with millions of files |
   | a file gets its own permission or moves folder | only the scope ID on that file's chunks — no reprocessing or re-embedding |

   In sync, permission is part of the diff.
5. **Filter before search, in every retriever** (dense, lexical, sparse, visual, graph,
   tables and forms, summaries): user + groups → readable scopes (SQLite query, cached in
   the session and invalidated when it changes) → pre-filter by the scope IDs, together with
   the other filters (retrieval, step 4).
6. **Aggregates never leak:**
   - folder summaries only over documents of the same scope — a folder with mixed scopes
     has one summary per scope;
   - graph relations and table and form rows inherit the scope of the source document;
   - counts in enumerative questions only count what the reader can see;
   - there is never an answer cache shared between users.
7. **Unknown or unreadable permission: deny by default** — only the workspace owner sees
   the document, and the source report points out the problem.
